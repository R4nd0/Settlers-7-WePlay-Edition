# RC4 launcher handoff — integration in progress

The process-local handoff in `tools/installer/crossplay_session.py` implements
the launcher side of the [version 1 production contract](GOLD-HISTORY-PRODUCTION-CONTRACT.md).
It does not enable mixed play in the launcher UI. Its production-adapter allowlist
is empty while the ordinary native runtime is being integrated. Existing release
adapters, including known legacy adapters accepted for repair, cannot receive an
explicit mixed launch through this boundary.

An explicit binding admits only Gold host / one Ubisoft or Steam History guest.
It validates the edition, role, port, session, independent client key and native
identity, common content digest and printable display name. Gold retains its
numeric identity namespace; History retains a separate 16-byte namespace. The
actual pinned executable and portable profile must belong to that same copy.
There is no supplied save token, checkpoint, native Ready/start value or map.

Every ordinary standalone start removes inherited `WEPLAY_CROSSPLAY_*` values,
case-insensitively. An explicitly admitted binding installs fresh values after
graphics configuration. The parent environment is unchanged, authentication
material is omitted from the binding's representation, and no session file is
written. Mixed launch does not obtain a remote native-game peer lease; the
existing executable-specific loopback policy remains mandatory.

The helper is included in the standalone package tool set. Refreshing a known
older Gold source package validates its original inventory, then adds all current
helper dependencies before inventorying and verifying the new package. Missing
new helpers are tolerated only when reading build input, never in fresh output.

Authored Python fixtures cover these boundaries and ordinary profile/graphics
and adapter migration behavior (85 tests passed on 2026-11-16, using Python
`-B` so fixture package inventories remain free of generated bytecode). A
separate private refresh of the actual previous Gold package passed its embedded
Python verification with the added helper and current UI, while retaining the
original template inventory. That fixture used an ordinary rebuilt AI adapter
and changed no checkout production pin. These checks do not establish live world start, save,
reload, checksum agreement or LAN/EasyTier qualification. RC4.00 publication
still requires both original History editions to pass mixed reload in the final
installed package, including continued original checksums and active logistics.

## Shared content admission

`crossplay_content.py` validates the contract's canonical three-edition catalog.
Each edition must include its pinned original executable and native adapter;
reviewed gameplay/script/map files are then frozen with the final qualified
profiles. The parser enforces exact schema/types, ordered editions and file IDs,
nonzero lowercase SHA-256 values, bounded size/counts and Windows-safe relative
paths. Duplicate JSON fields, case-colliding paths, links and local profile/save
inputs are rejected.

Schema validity supplies no release approval. `APPROVED_DIGESTS` remains empty
until the reviewed final catalog exists. An explicit standalone mixed launch
requires both an admitted production adapter and that exact approved catalog,
verifies the local installed files and requires the binding's content digest to
match. This prevents an arbitrary nonzero content value from reaching the game.
Ten catalog tests plus the nine handoff, seven migration and ten portable-runtime
tests pass. These are authored checks, separate from the required game tests.

## Owned local services

The reusable broker now lives in `tools/installer/crossplay_broker.py`; the
existing `tools/gold/crossplay_server.py` development command retains its entry
point and exports. Framing, authentication, projections, queue limits and EOF
behavior remain the existing implementation. Launch representations omit keys
and local identities.

`tools/gold/gold_session.py` owns exactly one Gold identity and three local
endpoints: authentication UDP, backend UDP and configuration HTTP. It reuses the
existing Gold protocol implementations, binds only `127.0.0.1`, accepts Gold's
`127.0.0.2` source and uses the contract's domain-separated HMAC password. The
explicit validated Gold principal matches the launch identity; the connection
identifier remains independently assigned. No second Gold launch is created.
The two Gold-only handoff ports are mandatory in `1024..65535`; History bindings
reject them.

`crossplay_runtime.SessionPump` pumps owned services and can attach to the owned
game handle. Game exit, cancellation or service failure releases its endpoints
and queues. There is no arbitrary healthy-game duration limit. Failure closes
the channel and reports a bounded error, leaving native disconnect handling to
the game. It does not terminate a healthy game.

The dependency list is explicit in package construction and installed launcher
sources. Nested Gold refresh adds all current service modules even when the
older source package does not list them. A fresh embedded-Python run imported
the complete 79-file refreshed Gold package, opened/pumped/closed its one-owner
service and verified the HMAC vector, with the old source inventory unchanged.
This used an ordinary AI adapter fixture and changed no production native pin.

On 2026-11-16, 239 targeted tests passed across local service sockets, broker,
handoff, content, lifetime, legacy Gold protocols, installation, migration and
desktop recovery. Authored protocol inputs and mocked process lifetimes remain
separate from actual native game qualification. RC4.00 remains unpublished.

## Host construction and private guest invitation

`crossplay_host.Host` verifies the approved local Gold content before opening
services. It constructs a fresh epoch, separate client keys and native identities,
then binds the Gold principal and local service ports to the host handoff. Its
private invitation includes only the guest's channel key and the existing private
EasyTier room token. The Gold host key is not exported. The guest rechecks its own
installed edition against the same approved catalog before creating its binding.

The invitation has an exact, bounded canonical format and fits the existing
private launcher channel. Unknown fields, malformed encodings, wrong roles and
content disagreement fail. Closed or retired sessions cannot issue new invites.
No map, save checkpoint or native Ready value is carried by this code.

Six additional integration tests pass, including actual authenticated loopback
relay for both History edition numbers with authored protocol clients. The refreshed
83-file Gold package separately imports the new host/invitation dependencies in
fresh embedded Python, round-trips the invitation and opens/closes the one-owner
Gold service. Actual game and EasyTier tunnel qualification remain pending.

## Scoped Windows transport integration

The Windows EasyTier worker now carries and echoes an explicit boolean mixed
scope. Its parent-process creation binding, protected IPC directory, interpreter
and helper inventory checks remain mandatory. Crossplay requires an admitted
native adapter before the worker starts the tunnel. The elevated worker checks
the standalone profile; the launcher separately verifies the approved gameplay
catalog before producing either native launch binding.

Mixed EasyTier ACLs permit only the broker's TCP `9113` to the coordinator and
its replies. Classic History-only ACLs keep their existing ports. The compiled
Windows helper has the same explicit scope and restricts the game-side transport
to the Python broker on the verified tunnel interface. It installs no remote
native-game rule in that scope. Gold roots additionally require their portable
descriptor and exact original prepared executable. Ordinary rule plans and
owned-name removal remain supported. No firewall change was applied by the
integration tests.

The gateway supports both a direct owned core and the elevated worker's live
process handle. Normal mixed sessions have no 30-minute gateway limit or worker
day limit; the owner still closes their endpoints on exit or cancellation.
Explicit bounded gateway durations remain available for development tests.

Unified Gold preparation now copies the common launcher, Python, .NET helper
and EasyTier runtimes from the verified package and includes them in its game
inventory and ownership tracking. Trusted worker verification admits only the
specific additional portable descriptor, policy helper and pinned Gold adapter;
it continues to reject unknown launcher files. Package construction requires the
compiled mixed-scope helper capability for platform-independent directory builds.

Validation on 2026-11-16: 206 targeted tests passed, including 11 read-only checks
against the newly compiled Windows helper. A fresh 460-file runtime package
copied 312 runtime/helper files into a minimal guarded Gold inventory fixture;
its embedded Python passed trusted-worker verification and the read-only compiled

## Pair transport ownership and managed Gold UI repair

`crossplay_network.NetworkSession` joins the approved host/guest bindings to the
owned Windows transport. Content and explicit connection consent are checked
before tunnel startup. Host mode opens its scoped listener before returning an
invitation, so the guest's virtual address need not be known in advance. Accepted
bytes remain unread until the owned tunnel reports that exact single guest.
Unknown participants, changed interfaces, loss of the owned worker and bounded
unconfirmed connections close the channel. End-to-end native authentication
remains in the broker.

Service shutdown joins the pump before removing its tunnel. Partial startup and
cancelled launches release their own resources; healthy game processes are never
terminated by this owner. Gold adapter cleanup now passes the same explicit
mixed scope to the compiled helper instead of validating a Gold root as a
History root. Ordinary cleanup keeps its existing scope.

Validation: 154 targeted service/package tests, 11 read-only compiled Windows
helper checks and the desktop package-identity regression passed. A fresh

the new owner in embedded Python. Its trusted inventory and compiled broker

## Gated desktop entry points

The desktop backend now has separate `crossplay-create` and `crossplay-join`
operations. They require the strict `crossplay_mixed` package capability, exact
request fields, explicit connection consent and the original local edition.
Before private-channel or tunnel startup, they verify the installed copy and
the approved catalog at `Payload/Crossplay/catalog.json`. Package validation
also binds the catalog to the actual shipped Gold and shared History adapters;
the feature flag alone grants nothing. Changes to this capability or catalog
invalidate the desktop's installed package identity and require an update.

The existing current-user private pipe carries invitations. The native launch
attaches to its service owner while the original game entry is still held;
the host invitation is returned only after native initialization. If a later
private-pipe or UI observer fails, the room closes while the parent waits for
the original game to exit. It does not terminate the healthy game. The ordinary
single-player and History-only multiplayer paths remain separate operations.

The Windows launcher has a gated Gold + History choice. Gold hosts explicitly
choose Ubisoft or Steam History; History can only join that mixed mode. An
unqualified package hides Gold's network entry. Private invitations stay masked
and their clipboard share text explains the matching mixed route. Original
Ready, map/save, AI and castle choices remain in the game.

On 2026-11-16, all 87 desktop/recovery tests, 35 installer tests and 12 content
catalog tests passed. The rebuilt launcher passed 41 bilingual rendered checks,
including synthetic capability changes, role restrictions, mandatory History

Production native/catalog approval sets remain empty and no release was made.

Registration diagnostics now expose fixed reason counters through the owned Gold

## Remaining game UI integration

The normal History archive already contains History-NEO5 hooks around network
start, Ready, save and restore. Mixed NEO19 must use its own production contract;
the existing History handshake cannot be represented as a mixed acknowledgement.
The final composition must preserve ordinary History-only behavior while routing
mixed lifecycle operations to their actual native implementation.

Gold's original game menu exposes Save/Load only in solo mode; its browser has no
usable multiplayer-resume route. The original multiplayer load/save dialogs do
exist. A separate, unembedded `mixed_save_interface.py` composition adds only the
original Save callback for an explicitly mixed running Gold host, checking the
original world/session/role/slot and excluding disconnect, desync and shutdown.
Solo retains Save and Load; a guest receives neither host action. Two Lua 5.1
tests pass. An in-memory composition of the real current Gold archive compiles
all 284 Lua members and changes only gameMenu; no game or deployment occurred.
This adds no save serialization, roster or NEO hook. The actual native save and
resume contract remains required before connecting this UI to the release.
